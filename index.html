~/case-study

Does a multi-agent code reviewer pay for itself?

I built a code-review agent out of several AI reviewers plus validators that try to knock down what they find. Then I built an eval to check whether all those agents were worth it. So far, a single reviewer has done just as well for about a fifth of the cost.

The question

Splitting code review across several specialised agents, then adding more agents to double-check their findings, sounds thorough. It also costs several times more per pull request. I wanted to know whether the extra agents catch bugs that a single pass misses.

What I built

Note 1A test runs against the sandbox itself and checks that network calls, writes outside the working folder and reads of credential folders are all blocked.

I built it for my own code reviews. Each review runs headless in an OS sandbox: no network, no credentials, and it can write only to its own working folder.1 Three reviewers read the diff, each looking for a different kind of problem, and every finding has to name what triggers it, what goes wrong and the exact line. A separate validator then tries to prove each finding wrong: it looks for a check elsewhere that makes the code safe, confirms the bad path can actually happen, and runs the smallest test it can. Nothing is posted to GitHub; I read what it found and decide what to say.

I designed it, specified it and reviewed the changes; it was implemented with AI coding agents (Claude Code, Codex and Cursor).

How I measured it

The test set had to be real bugs in real code. I took about 2,100 merged pull requests from the product I work on and pulled out two kinds of bug: ones reviewers caught, and ones that slipped through and were fixed later. For each slipped bug, an agent had to show it really existed in the pull request that introduced it; more than half failed that check and were thrown out. Added to the cases I already had, that gave 230 test cases: 162 pull requests with 225 known bugs between them, and 68 with no known bug.

I split the cases into a set I tune against and a held-out set I never tune against. A judge model decides whether each review found each known bug, and every score comes with a 95% range. Each run puts both designs on the same pull requests: one reviewer, or the full multi-agent pipeline.

What I found

Neither run shows a real difference in bugs found. On the first, smaller run the pipeline found two more (13 of 15 against 11 of 15); on the second it found fewer (42 of 55 against 46 of 56). Either way the ranges overlap. The cost gap is real: the pipeline cost about 4.7 times as much on the first run and 4.9 times as much on the second.

What this doesn't show

The second run isn't finished: both designs have been scored on 53 of its 82 pull requests. The known bugs were labelled by agents, not checked by a person, and one judge model did all the scoring. I also only measured whether bugs were found, not how many false alarms each design raised. That last one is where the extra agents could still earn their cost.

So far the simpler design wins on cost and ties on bugs found. I'd want the false-alarm numbers before calling it settled.

~/beliefs

What I believe about agents

  1. Measure before adding agents.

    More agents cost more on every run. Check that they find more before you keep them.

  2. Never tune on the holdout.

    Once you tune against your test set, its scores stop telling you anything about new code.

  3. Ship the caveats with the number.

    Put what a result doesn't show right next to it, not in a footnote.

  4. Guardrails belong outside the model.

    A prompt that says 'don't' is a request. A sandbox with no network or credentials is a guarantee.
